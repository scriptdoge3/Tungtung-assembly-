How the server works

The whole server is one loop of raw Linux syscalls. Here is the life of a request:

1. Boot

socket(AF_INET, SOCK_STREAM, 0)          ; get a TCP socket
setsockopt(fd, SOL_SOCKET, SO_REUSEADDR) ; allow fast restarts
bind(fd, {AF_INET, port 8080, 0.0.0.0})  ; claim the port
listen(fd, 16)                           ; start accepting

The port lives in the binary as two literal bytes, because the kernel wants it in network byte order:

sockaddr:
    .word  AF_INET
    .byte  0x1f, 0x90        ; 0x1F90 = 8080, big-endian
    .long  0                 ; INADDR_ANY

2. Receive the HTTP request

accept(2) gives us a client socket, read(2) gives us the raw bytes of the request. The method check is a single 4-byte compare — the string "GET " is the little-endian dword 0x20544547:

cmp  dword ptr [rsi], 0x20544547   ; "GET " ?
jne  send_405

Then a byte-by-byte scan slices the path out of GET /path HTTP/1.1 by overwriting the first space with a NUL.

3. Route

The path is compared against /, /index.html, /about and /how with a tiny hand-written string compare. Anything else falls through to the 404 page.

4. Send the HTTP response

The response is written manually in four pieces:

  1. a header prefix ending in Content-Length:
  2. the body length, converted to decimal digits by a hand-written itoa (repeated div 10, digits filled right to left)
  3. \r\nConnection: close\r\n\r\n
  4. the HTML body itself, which was embedded into the binary at build time with the assembler directive .incbin "www/index.html"

Every piece goes out through a loop around sendto(2) with MSG_NOSIGNAL, so short writes are resumed and a client that hangs up early cannot kill the server with SIGPIPE.

5. Repeat

close(client)
jmp accept_loop

That is the entire request lifecycle. No framework, no event loop library, no allocator — the server never even calls mmap or brk. All memory is static.
